# Контекст заявок и загрузка — 09.11.2026

## Поведение

В уведомлении MAX и карточке заявки выделен контекст обращения:

- источник формы: карточка модели, конкретная планировка, общая форма,
  шапка, закреплённая форма, квиз, расчёт, производство или основание;
- происхождение каждого параметра: самостоятельное переключение, контекст
  планировки, исходная ссылка, значение на экране по умолчанию либо неизвестно;
- последние три полезных действия после согласия на аналитику, если есть
  действующее согласие с подписанным серверным идентификатором;
- способ связи: переключён клиентом либо предложен формой и подтверждён отправкой.

Пополненные поля старых заявок не доказывают самостоятельный выбор. История
задним числом не восстанавливается. Старые уведомления не пересылаются.
Функциональное происхождение выбора хранится только в памяти страницы до
отправки формы. Контакты и произвольный текст не попадают в историю действий.
Отзыв согласия и срок 180 дней удаляют копию истории из CRM-контекста заявки;
содержание самой заявки и её статус сохраняются.

Основная кнопка модели запрашивает предложение; запрос конкретной планировки
доступен из её просмотра. Наличие первой планировки в URL само по себе не
превращает обычное обращение в запрос её расчёта. Общие формы не представляют
унаследованный расчёт как подтверждённую конфигурацию клиента.

Старые клиенты без intentContext принимаются. Для них показывается отсутствие
сведений о происхождении параметров. Цены и исходные контракты форм сохранены.
При повторе отправки неизменность бизнес-полей проверяется; отличающийся телефон
даёт 409. Обновившаяся служебная история не мешает повтору, уведомление использует
сохранённый первый снимок. Доставленные заявки повторно не отправляются.

MAX ограничен 4000 символами: при переполнении сохраняются контакт, контекст,
сумма расчёта и ссылка на полную карточку менеджера. Ссылка требует обычную
авторизацию/MFA; доступ по номеру заявки не предоставляется.

## Загрузка

Разные query-версии journey-tracker.mjs теперь переэкспортируют один общий runtime.
Это убирает повторные очереди, обработчики, запросы конфигурации и таймеры.
На главной добавлен modulepreload runtime, чтобы не создавать лишний каскад.

Для изображений, шрифтов и GLB предусмотрен Cache-Control:
public, max-age=0, must-revalidate. Файлы сохраняются локально, но перед повторным
использованием сервер подтверждает их актуальность. Картинки не перекодируются.
HTML, скрипты, API, кабинет, CRM и JSON с ценами не затрагиваются.
Не заявляется измеренное ускорение первой загрузки или процентный прирост.

## Проверки и публикация

78 Node-проверок: API, MAX-заглушка, идемпотентность, согласие, анонимные счётчики,
источники, права, MFA, окружение стенда и комплектации.
Две Python-проверки: узкое изменение Caddy и аудит SQLite только для чтения.
В production не создаются фиктивные заявки и не отправляются тестовые сообщения.

Пакет накладывается на CONSENT-9bfb50e7d228 после сверки полных деревьев web/API.
Привилегированная публикация делает согласованный backup SQLite с проверкой
восстановления и аудит всех сохранённых заявок. Выход аудита — только счётчики
и утверждённые категории, без контактов, комментариев и идентификаторов клиентов.

Изменение Caddy защищено SHA исходной конфигурации; синтаксис проверяется до sudo,
полная валидация до установки. При изменившейся конфигурации кеширование пропускается.
После установки проверяются неизменность файлов, ETag/304 и no-store динамических
страниц. При ошибке возвращаются прежние web/API и конфигурация Caddy. Старая БД
поверх поступивших новых заявок не восстанавливается.

Результат выпуска и обезличенный аудит сохраняются локально в
.local/lead-intent-20261109/deployment-result.json; приватные backup остаются на сервере.
