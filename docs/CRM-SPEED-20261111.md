# Кабинет заявок, баннер акции и загрузка сайта — 11.11.2026

## Результат

К существующей CRM добавлены отдельный профиль клиента и журнал контактов. Ответственный выбирается по ID действующей учётной записи, а не вводится произвольным текстом. Имя, регион, населённый пункт, следующий контакт и рабочая заметка редактируются в карточке. Сообщения, звонки, встречи и заметки фиксируются с автором и временем; это журнал, отправки сообщений клиенту из него нет.

Фильтры комбинируются: статус, менеджер, модель, регион, населённый пункт, источник, канал трафика, кампания, страница/форма, период по Москве, просроченный следующий контакт. Поиск ищет в том числе по тексту журнала, учитывает кириллицу и ё/е, а символы `%` и `_` трактует буквально. Есть постраничная загрузка. Конкурирующие изменения карточки обнаруживаются по версии, повторная отправка одной записи журнала не создаёт дубль.

Исходный `snapshot_json`, идентификатор запроса и квитанция доставки MAX неизменяемы. Профиль хранится в `crm_lead_profiles`, журнал — в `crm_lead_activity`. Тестовые заявки остаются только для чтения. Сервер проверяет сессию, Origin, CSRF и права при каждой записи; автора из браузера не принимает.

Имена трёх уже существующих сотрудников приводятся к полным именам: Сергей Ярушкин, Юрий Ярушкин, Михаил Хапов. Сопоставление с учётными записями находится только в закрытом пакете публикации. Миграция не создаёт пользователей и не меняет пароли, активность, роли или MFA.

На главной через 1,5 секунды просмотра цен появляется небольшое немодальное уведомление: случайно выбранный «Парус» или «Квадро Хаус», даты 11–21 ноября и крестик. Цены и основная кнопка не перекрываются; сайт остаётся доступен. На узком экране баннер превращается в компактную горизонтальную карточку. Если безопасного свободного места нет, он ожидает подходящего положения страницы. Закрытие запоминается до конца вкладочной сессии без идентификатора посетителя. Переход ведёт на `/blackfriday/` с текущей моделью, размером, комплектацией и разрешёнными рекламными метками.

## Аудит архитектуры

Основа уже подходящая: статический HTML, собственные ES-модули, Caddy, отдельный API с SQLite. HTML доступен до выполнения клиентского кода; первый hero уже имел адаптивный `srcset`, preload и высокий приоритет. Zstandard/Gzip для текстовых ответов уже включены. Интерактивный 3D уже загружался по нажатию, а не вместе с первым экраном. Эти решения сохранены.

Обнаруженные потери и исправления:

| До | После |
|---|---|
| 37 начальных JS-адресов с каскадом импортов | 3 адреса: главная сборка, общий модуль, прежний ScrollCraft |
| 263 179 байт исходного начального JS | около 213 КБ; gzip около 59 КБ против 92 КБ |
| Два прайса 231 167 + 231 086 байт | общий набор витрины 1 905 байт, встроен в сборку |
| Три блокирующих CSS-запроса | одна CSS-сборка с тем же порядком правил |
| Повторная проверка каждой картинки и шрифта при возвращении | 181 побайтно идентичная копия с хешем в URL и immutable-кешем |
| GLB передавались без сжатия | отдельное Zstandard/Gzip-сжатие только публичных GLB |
| Нижние чертежи начинали загрузку сразу | native lazy loading и async decode |

Проверенный пример GLB: 2 676 632 → 759 228 байт в gzip, сокращение передачи примерно на 72%. Распакованный SHA-256 совпадает с исходником. Палитра, геометрия, двери и выдвижной полок не менялись.

Показатели в таблице описывают состав ресурсов, а не обещание времени загрузки на любом устройстве. Полевые LCP/INP/CLS не измерялись: нельзя подменять их статическим аудитом или временем ответа через VPN. Первый вход всё ещё требует загрузить исходное изображение выбранного разрешения; повторный вход использует кеш. Большие фотографии не пережимаются, исходные файлы не удаляются.

Сборка esbuild закреплена lock-файлом. Исходники всех 48 используемых модулей и данных синхронизированы с проверенным действующим релизом; список `scripts/performance-sources.json` делает изменения этих исходников входом следующей сборки. Статические и динамические импорты используют одно каноническое имя модуля, поэтому аналитика и отправка заявки не получают несколько экземпляров состояния из-за разных `?v=`. 3D и квиз вынесены в отдельные динамические части. Квиз инициализируется после первого рендера либо сразу при обращении к нему. Единственный компактный набор цен сверяется со всеми 20 размерами и 40 ценами. Канонические прайсы калькулятора/API не меняются.

Версионные URL применяются к изображениям, шрифтам и готовым сборкам. HTML, кабинет, CRM и API сохраняют `no-store`. Старые публичные URL сохраняют revalidation. Кеш не получает персональные данные. Service Worker и сторонний CDN не добавлялись: для этого сайта полезнее убрать каскад запросов и лишние данные, сохранив прозрачное обновление цен и заявок.

Первичные технические источники:

- [Google: оптимизация LCP](https://web.dev/articles/optimize-lcp) — раннее обнаружение главного изображения, preload/fetchpriority, отказ от lazy loading для hero.
- [esbuild: splitting и metafile](https://esbuild.github.io/api/) — сборка общих и динамических частей, контроль состава ресурсов.
- [Caddy: encode](https://caddyserver.com/docs/caddyfile/directives/encode) — типы ответов, negotiation и обратимое сжатие. `model/gltf-binary` отсутствует в стандартном списке.
- [Caddy: header](https://caddyserver.com/docs/caddyfile/directives/header) — отложенные, взаимоисключающие правила кеша и ограничение успешными ответами.

## Проверки

76 тестов: заявки и дедупликация, MAX через локальную заглушку, 40 цен акции без дополнительной скидки 20 тысяч, базовый прайс, исходные/default-параметры, CRM-права, Origin/CSRF, MFA и сохранённые устройства, неизменность исходных заявок, журнал/фильтры/конфликты. Проверка сборки подтверждает сохранность body-разметки главной с точностью до технических адресов ресурсов. На сервере повторно проверяются импорты API, синтаксис модулей, 40 цен, полные деревья файлов и Caddy.

Браузер: карточка клиента и назначение менеджера, сохранение и поиск заметок; главная и мобильный экран 390×844; 3D, приближение, двери и нижний полок; CTA конкретной планировки; успешная заявка в локальной заглушке, в тексте MAX есть только шифр планировки. На действующий MAX фиктивные заявки не отправляются.

## Сборка и публикация

1. `scripts/capture-workspace-baseline.py` снимает read-only инвентарь актуальных публичных релизов. Пароли/клиенты не выгружаются. Локальная копия пополняется только файлами с совпавшим SHA-256.
2. Установить закреплённый esbuild: `pnpm install --frozen-lockfile`. `node scripts/build-workspace-release.mjs` собирает узкую накладку поверх проверенной текущей страницы. Список файлов и метаданные находятся в `.local/crm-speed-20261111/build.json`.
3. Подготовить в закрытом `.local/crm-speed-20261111/staff-names.json` сопоставление трёх существующих аккаунтов (`phone`, `name`). Этот файл не коммитится.
4. `scripts/prepare-workspace-release.py` создаёт пакет; `scripts/upload-workspace-release.py` передаёт его частями и выполняет read-only preflight. Каталог публикации включает только зафиксированные файлы с проверенными хешами.
5. `scripts/publish-workspace-terminal.py` запрашивает sudo один раз и запускает отсоединённую задачу. Обрыв SSH не останавливает публикацию; состояние и квитанция сохраняются на сервере и перечитываются при переподключении.

Перед переключением выполняются согласованная резервная копия базы и восстановление в изолированный файл. Новая миграция сначала проверяется на этом восстановлении. Действующая база получает только дополнительные таблицы, имена существующих сотрудников и привязку однозначно распознанных прежних назначений; исходные заявки остаются прежними.

Два симлинка web/API переключаются на новые каталоги, перезапускается только существующий сервис API. Caddy меняется только в блоке DachaPar: immutable для `/assets/fast/` и `/assets/build/`, сжатие публичных GLB. Другие продукты, порты, домены, firewall и SSH не меняются. Кандидат Caddy проверяется до установки. При ошибке восстанавливаются прежние симлинки и конфигурация Caddy; старая база поверх новых заявок никогда не восстанавливается.

После публикации: проверить `/manager.html`, открыть реальную карточку без изменения, список трёх менеджеров, фильтры; на главной модель/размер/комплектацию, чертёж и 3D; баннер около цен; успешные статические хеши; `401` без авторизации и `400` на пустую заявку. Автоматическая квитанция хранится в `.local/crm-speed-20261111/deployment-result.json`; серверная резервная копия и путь отката указаны в ней.
