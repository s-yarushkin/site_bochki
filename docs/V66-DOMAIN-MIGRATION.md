# Гарант Бани — перенос сайта, менеджерского кабинета и заявок на другой домен

**Статус:** план миграции; НИКАКИХ действующих переносов или изменений DNS/серверов.

## Состав системы
1. Статический сайт и конфигуратор: HTML, JS, CSS, фотографии; `data/catalog-pricebook.json` — цены, варианты размеров, цвета, комплектация.
2. Backend: `server/garant-bani-relay.mjs`, `server/manager-api.mjs`, `server/manager-auth.mjs` на Node.js, API `/api/lead`, `/api/manager/*`.
3. Состояние: `/var/lib/garant-bani-relay/leads.sqlite` (заявки, снимки расчётов, статусы, заметки, события). SQLite использует WAL, поэтому **нельзя** просто копировать открытый основной файл без согласованного SQLite backup/checkpoint.
4. Учётные записи менеджеров и криптографический секрет сессий: отдельные защищённые файлы `/etc/garant-bani-preview/manager-accounts.json`, `/etc/garant-bani-preview/manager-session-secret`, MAX credentials и `relay.env`. Никогда не помещать их в публичную директорию и Git.
5. HTTP и TLS: Caddy, точные маршруты хоста, cert issuance, сохранение старого домена на период переключения.

## Доменно-независимые настройки V6.6 (изменение кода в отдельной ветке)
- `ALLOWED_ORIGIN`: **полный точный HTTPS origin** домена, который обслуживает формы; проверки Origin остаются строгими.
- `SITE_BASE_PATH`: `/bani-preview/` для текущего тестового размещения или `/` для отдельного корневого сайта. Без подмены кода корректно вычисляется `Path` защищённой менеджерской cookie.
- Внутренний адрес обработчика остаётся доступным только через loopback/reverse proxy; клиент формирует API URL относительно `document.baseURI`; proxy переписывает публичный prefix на `/api/*`.
- `LEADS_DB_PATH`: отдельный постоянный защищённый SQLite data volume. При переходе на другой сервер сохранить путь или сконфигурировать отдельную согласованную миграцию данных.
- Актуальный прайс JSON и приложение должны быть **одного проверенного релизного SHA**; backend рассчитывает цены заново, не доверяет заявленной сумме браузера.

## План cutover (только по отдельной команде владельца)
1. Записать точный SHA исходников, резервный релиз и контрольные суммы текущих конфигураций. Создать закрытый snapshot/SQLite backup и отдельно сохранить секреты, права/владельца файлов; проверить integrity_check и количество заявок/событий.
2. Предварительно настроить HTTPS на новом домене и закрытый тестовый route, не открывая внешнему трафику менеджерский кабинет.
3. Поднять сервис с новым `ALLOWED_ORIGIN`, `SITE_BASE_PATH`, скорректированными системными настройками и сертификатом. При переезде на другой сервер восстановить DB/секреты в закрытых каталогах, проверить права.
4. Smoke на новом домене: 4 модели × все размеры, готовый комплект, две формы с согласием, существующие заявки и статусы менеджеров, login/logout, CORS/Origin, MAX receipt и хеш версии прайса. Не отправлять реальные тестовые заявки в MAX без согласования.
5. Заморозить операции с заявками на короткое время cutover, финальный консистентный backup/transfer и сверка контрольных сумм. Не вести две самостоятельные активные SQLite базы.
6. Переключить DNS/маршрут после owner acceptance. Старый домен сохранить как безопасный редирект; не публиковать открытый путь к архивам/секретам. Менеджеры войдут заново на новом домене (браузерные cookie нельзя переносить между доменами).
7. Проверить доступность, формы, выдачу менеджеру и целостность данных; уметь откатить DNS/сервис, соблюдая единственный источник записей; сохранить резервные копии до окончания окна наблюдения.

## Что переносится без потерь при выполнении протокола
- Исходный код, цены/комплектации, изображения, интерфейсы, менеджерские логины и хеши паролей, сохранённые заявки/примечания/статусы и журнал изменений.
- Сеансы браузера/старые cookie **не** переносятся; после смены домена нужен новый логин.
- Сертификаты домена выдаются/настраиваются заново, значения Origin и cookie Path обновляются конфигурацией.

## Границы
Этот документ не проводит миграцию и не меняет действующие Caddy, MAX, SQLite, DNS. Любые работы на новом домене требуют точного hostname, согласованного обслуживания существующих пользователей и отдельного read-only preflight + rollback.
