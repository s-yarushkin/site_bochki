# Гарант Бани — кабинет заявок (MVP)

## Цель и границы

- MAX-группа получает уведомления с идентификатором заявки `GB-YYYYMMDD-XXXXXXXX`, полным составом выбранных опций и ценами, скидкой, отделкой, параметрами участка, контактами и каналом связи.
- Отдельный кабинет менеджера: `https://дизайн-завод.рф/bani-preview/manager.html`.
- Заявка **сначала сохраняется в SQLite**, затем отправляется в MAX. Если MAX недоступен, запись остаётся со статусом `failed`. Интерфейс клиента не должен показывать доставку до успешного ответа API.
- В кабинете менеджер может искать заявки, фильтровать по статусу, просматривать все выборы покупателя, менять статус, назначать ответственного и сохранять заметку. История изменений не перезаписывается.
- Действующий сайт «Диззавод» (`/`, `/api/lead`, `/api/analytics/event`) не изменяется. Прежние MAX-боты не используются.
- Сайт «Гарант Бани» пока под паролем. Реквизиты ИП в Политике и Согласии незаполнены, публичный выпуск запрещён до их заполнения и юридической проверки.

## Архитектура

| Слой | Реализация |
|---|---|
| Сайт клиента | `/srv/sites/garant-bani-preview/current` |
| Кабинет менеджера | Статические `manager.html`, `assets/js/manager.js`, `assets/css/manager.css` |
| API | Изолированный `garant-bani-relay.service` (`127.0.0.1:3301`) |
| Публичная форма | POST `/bani-preview/api/lead` → внутренний `/api/lead` |
| API менеджера | `/bani-preview/api/manager/*` → внутренний `/api/manager/*` |
| База | `/var/lib/garant-bani-relay/leads.sqlite` (SQLite, WAL, private state dir) |
| Менеджер | Отдельная парольная авторизация через `POST /api/manager/login` |
| Доступ | И действующий BasicAuth предпросмотра, и дополнительная авторизация менеджера; cookie HttpOnly/Secure/SameSite=Strict на 8 ч |
| Секреты | systemd `LoadCredential` из `/etc/garant-bani-preview`, root:root, 0600 |
| Уведомления | MAX `-79890208563249`, токен вне GitHub |
| История | Таблица `lead_events`, запись всех изменений |
| Идемпотентность | Ключ `requestId` в форме и уникальный индекс в БД |

## Статусы

`new`, `in_progress`, `awaiting_customer`, `quote_sent`, `won`, `lost`.

Уведомление MAX имеет **отдельный** статус: `pending`, `delivered`, `failed`. Отсутствие сообщения MAX не означает потерю заявки.

## Миграция и активация

1. Проверить релиз: `npm test`, статические контракты, браузерный smoke на 390/320 px, тесты idempotency/auth/storage.
2. Убедиться, что системный Node.js поддерживает `node:sqlite` (Node 22.5+; предпочтительно 24+).
3. Получить два архива из **точного** принятого SHA, проверить SHA256 и состав.
4. Записать секреты root-only:
   - `manager-password-hash`: `scrypt$<32-hex-salt>$<128-hex-hash>`. Ввод пароля только интерактивно в терминале, не в аргументах процессов и не в чате.
   - `manager-session-secret`: случайный hex минимум 64 символа.
5. Создать отдельный релиз обработчика, установить новый unit из `ops/systemd`, установить `StateDirectory=garant-bani-relay` с режимом 0700. **Не очищать state dir при релизе или откате.**
6. Подготовить и валидировать Caddyfile, дополнить **только** существующий внутренний `route` внутри `handle_path /bani-preview/*` маршрутом:
   ```caddy
   @baniManagerApi path /api/manager/*
   handle @baniManagerApi {
       reverse_proxy 127.0.0.1:3301
   }
   ```
   Маршрут нужно разместить перед завершающим `handle { file_server }`. Basic Auth предпросмотра должен применяться и к этому API. Выполнить `caddy validate`.
7. Сделать backup Caddyfile; релиз backend и candidate Caddy, протестировать `GET /health`, отказ без login (`401`), login и list, отказ при CSRF, сохранение статуса. Не отправлять клиентские данные в лог. Проверить открытые пути `/api/lead` и `/api/analytics/event` Диззавода (GET=405).
8. Переключить статический каталог только после того, как backend, база, авторизация и Caddy API работают. При любой ошибке вернуть текущие ссылки `current`, unit и Caddyfile из backup.
9. Проверить две реальные заявки с тестовыми номерами в MAX. Проверить, что они появились в кабинете, детали совпадают, смена статуса сохраняется и история видна.

### Защита и эксплуатация

- Параметр `requestId` не позволяет создавать дубли при повторном нажатии «Отправить».
- Список и карточка менеджера доступны только с подписанной cookie; API не использует BasicAuth предпросмотра как замену авторизации менеджера.
- Запросы, изменяющие данные, должны иметь корректный Origin, а cookie — SameSite=Strict.
- Обработчик не записывает номера клиентов, персональные комментарии и пароли в системный журнал.
- Перед публичным запуском определить фактический срок хранения заявок, процедуру удаления и права доступа к персональным данным (152-ФЗ), резервное копирование SQLite вместе с WAL через SQLite backup API / остановку службы; не копировать работающую DB без учёта WAL.
- Цена демопрототипа не является офертой; менеджер обязан подтверждать условия.
- Если клиент выбрал мессенджер, доступность его аккаунта по номеру зависит от настроек приватности. При необходимости уточнить удобный способ связи звонком.

## Rollback

- Вернуть обе ссылки `current` на прежние релизы, а также backup Caddyfile и unit, перезапустить только `garant-bani-relay.service` и reload Caddy.
- **Базу `/var/lib/garant-bani-relay/leads.sqlite` не удалять и не откатывать.** Она содержит реальные клиентские данные; сначала обеспечить их сохранность.
- Убедиться, что `Диззавод` и его сервисы не изменились.

## Оставшиеся задачи перед публичным выпуском

- Заполнить реквизиты ИП, окончательно утвердить Политику и отдельное согласие.
- Юридически проверить способ фиксации согласия, сроки хранения, условия обработки у MAX/хостинга и локализацию персональных данных.
- При необходимости добавить журнал назначенных менеджеров по пользователям и ролевую модель, отдельные учетные записи (MVP сейчас: общий доступ менеджера с единым секретом).
