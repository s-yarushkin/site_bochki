# Дача Пар — Gallery V2, проверенный локальный RC (22.10.2026)

## Решение владельца

Фотографии выполненных объектов связаны только с `modelId` и `objectId`. Пример выполненных работ **не содержит цены, размера, точной комплектации или планировки**. Планировки — отдельные материалы внутри модели, каталог цен и калькулятор — отдельно. Для передачи будущих фотографий четыре ключа: `kvadro`, `viking`, `parus`, `kvadro-house`. В `assets/gallery-v2/catalog.json` сейчас только публично известные обложки четырёх моделей; четыре серии и 29 кадров Паруса в прежнем черновом реестре ждут качественного одобренного web-export. Они намеренно НЕ публикуются и не входят в этот RC.

## Что уже написано

- `assets/gallery-v2/gallery.mjs`: полноценный modal gallery с названием модели, группами объектов, ракурсами, миниатюрами, предыдущим/следующим кадром, клавиатурой/Esc, свайпами, возвратом фокуса и ссылкой на существующую страницу модели. Не вызывает API и не трогает конструктор/цену.
- `assets/gallery-v2/gallery.css`: отдельные токены и адаптивные стили. Главное `img.dp-main-image` занимает **100% ширины и высоты `.dp-stage`** с `object-fit:contain`; правила миниатюр не влияют на него даже при конфликтующем внешнем CSS.
- `assets/gallery-v2/small-image-guard.mjs`: **отдельный P0-защитник** для уже существующей галереи. Его функция `detectAndRepairTinyStageImage(root)` доступна для точечного вызова **только после просмотра исходников опубликованного виджета**. Не импортируется в production автоматически.
- `ops/prepare_gallery_v2.py`: создаёт staging-копию текущей статической версии, не перезапуская сервисы. Не заменяет production. Если в HTML обнаружен `/parus-media/`, требует явного подтверждения изучения этого модуля.
- `tests/browser_gallery_v2.py`: изолированная браузерная матрица без внешнего трафика; отдельное синтетическое воспроизведение 44×58 px внутри 1020×480 px, затем исправление. Тест проверяет, что миниатюра остаётся маленькой.
- `ops/gallery-v2-live-probe.ps1`: read-only загрузка трёх актуальных публичных модулей и HTML в temp Windows с SHA-256 — чтобы привязать P0 к фактически опубликованному коду. Нет запросов POST, не читает SQLite.

## Фактически выполненные тесты на локальных файлах

`node --check assets/gallery-v2/gallery.mjs` PASS; `node --check assets/gallery-v2/small-image-guard.mjs` PASS; `python -m py_compile ops/prepare_gallery_v2.py tests/browser_gallery_v2.py` PASS; `python tests/browser_gallery_v2.py`: **112/112 PASS**, viewports 390, 768, 1366, 1920. Для P0: broken image=44×58, fixed image≥1000 px, thumbnail≤50 px. Образцы для теста — простые локальные SVG-плашки, **не фотографии продаваемой бани**. `prepare_gallery_v2` на синтетической статической копии PASS.

## Что ещё НЕ проверено — запреты на деплой

1. Нельзя считать P0 на live устранённым: фактический `/parus-media/widget.mjs`, `widget.css`, `content.mjs` отсутствует в этой доступной ветке, а публичный домен не отвечал из данной среды. Нужен код опубликованного виджета и проверка его реального DOM на Windows Chromium.
2. Новый компонент ещё не встроен в опубликованный сайт; интегрируется только через staging и тест существующих взаимодействий. Не заменять богатую галерею Паруса одиночной обложкой.
3. Нужна регрессия 4 модели × desktop/mobile; 2 темы, закрытие/навигация, 4 группы Паруса после публикации web-media, страницы моделей, формы/конфигуратор, MAX и SQLite через отдельные безопасные тесты; origin + SEO; native manager login / 2FA read-only. Принять только точный release SHA и сохранить rollback.
4. **NO PRODUCTION DEPLOY / NO MERGE** до sign-off. GitHub Actions не использовать.

## Как подготовить источник для проверки P0 на Windows без изменения сайта

`powershell -ExecutionPolicy Bypass -File .\ops\gallery-v2-live-probe.ps1`

Результат: пути к скачанным публичным файлам и их SHA-256. Сверить исходники и диагностику DOM, исправить конкретный опубликованный виджет. Только затем включать новую галерею и выполнять browser acceptance.
